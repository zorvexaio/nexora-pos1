# تحديثات Nexora POS وحماية بيانات العميل

## المبدأ

ملفات البرنامج المثبتة قابلة للاستبدال في كل إصدار، أما حالة العميل فتظل في مجلد Electron `userData` الخاص بالتطبيق. لذلك لا يضع التطبيق قاعدة البيانات أو الصور أو الترخيص أو شهادات شبكة LAN داخل مجلد التثبيت أو `app.asar`.

ما يبقى بين الإصدارات:

- `pos.db`: بيانات نقطة البيع كاملة، مشفّرة.
- `pos.db.key`: مفتاح قاعدة البيانات المحمي بحساب Windows نفسه.
- `product-images/`: صور المنتجات والشعار.
- `license.lic`، `pos-crl.json`، `device-id.txt`، `license-last-seen.bin`: حالة الترخيص.
- `lan-sync.db` و`lan-tls-*.pem` و`terminal-invoice-id.txt`: حالة الربط بين أجهزة المحل.
- `app_settings` داخل القاعدة: كل الإعدادات، ومنها تفضيل التحقق التلقائي من التحديث.

لا يجب تغيير `build.appId` (`com.zorvexa.nexorapos`) أو اسم المنتج أو مسار `userData` في إصدار لاحق؛ ذلك قد يجعل التطبيق الجديد يبحث في مجلد بيانات مختلف.

## ترحيل قاعدة البيانات

عند التشغيل، تُنفّذ الترقية داخل معاملة SQLite واحدة. يسجل الجدول `schema_migrations` والـ `PRAGMA user_version` آخر مستوى مخطط وصل إليه الجهاز. قبل أول ترقية لقاعدة قديمة، ينشئ التطبيق لقطة كاملة في:

`%APPDATA%\Nexora POS\upgrade-backups\<timestamp>-schema-vX-to-vY`

تتضمن اللقطة كامل `userData` باستثناء اللقطات القديمة نفسها، وبعد دمج WAL في `pos.db` والتحقق من أن النسخة قابلة للفتح بالمفتاح الحالي. إذا فشلت أي ترحيلة تُلغى المعاملة ولا يستمر التطبيق بقاعدة نصف مُرحّلة.

لإضافة ترحيلة مستقبلية:

1. ارفع `CURRENT_SCHEMA_VERSION` إلى رقم جديد.
2. أضف ترحيلة جديدة لا تعدّل أي ترحيلة منشورة، باستخدام `applyVersionedMigration(version, name, migration)` داخل معاملة `init`.
3. اجعل التحويل idempotent حيث يمكن، واختبر قاعدة قديمة حقيقية ونسخة جديدة فارغة.
4. لا تحذف أعمدة أو جداول تحمل سجلات مالية مباشرة؛ استخدم إضافة/نسخ/تحقق ثم أزلها فقط في إصدار كبير مخطط له.

## التحقق والتحديث

يستخدم الإصدار `0.48.0` مزود `electron-updater` من GitHub Releases للمستودع `zorvexaio/nexora-pos`.

1. يتحقق التطبيق الموزع من وجود إصدار عند التشغيل افتراضياً، دون تنزيل شيء.
2. المدير يراجع التحديث من الإعدادات ويختار التنزيل.
3. بعد اكتمال التنزيل، عند اختيار **التثبيت وإعادة التشغيل** ينشئ التطبيق لقطة استرجاع كاملة موثقة ثم يستدعي المثبّت.
4. لا يتم تثبيت تحديث تلقائياً عند إغلاق البرنامج العادي؛ هذا يمنع تجاوز لقطة الاسترجاع.

إصدارات GitHub يجب أن تكون قابلة للقراءة من أجهزة العملاء. إذا كان المستودع خاصاً، لا تُضمّن رمز GitHub في التطبيق ولا تستخدم حساب العميل للوصول إليه. انشر بدلاً من ذلك ملفات التحديث الموقعة في endpoint عام مخصص، ثم استبدل `publish` بمزوّد generic HTTPS مضبوط بالمصادقة المناسبة من جهة الخادم.

## نشر إصدار جديد

1. ارفع `version` في `package.json` و`package-lock.json` و`VERSION` وفق SemVer.
2. شغّل `npm run check` ثم ابنِ نسخة Windows موقعة بشهادة Authenticode صالحة.
3. لإنشاء ورفع أصول التحديث إلى GitHub Release استخدم، في بيئة نشر تملك `GH_TOKEN` بصلاحية إنشاء releases: `npm run dist:win:publish`.
4. أنشئ Release عادي غير Draft وغير Prerelease وبنفس رقم الإصدار (`v0.48.0` مثلاً). يجب أن يحتوي على جميع الملفات التي يولدها electron-builder، لا سيما:
   - `Nexora-POS-Setup-<version>.exe`
   - ملف `.blockmap` المقابل
   - `latest.yml`
5. لا تستبدل أصول Release منشور. أنشئ إصداراً جديداً دائماً، واحتفظ بالإصدار السابق لتسهيل التراجع.
6. اختبر التحديث على جهاز عميل تجريبي لديه بيانات فعلية: فحص، تنزيل، لقطة، تثبيت، إعادة تشغيل، ثم تحقق من المبيعات والإعدادات والصور والترخيص.

الإصدارات الأقدم من 0.48.0 لا يملك مزود تحديث مكتمل، لذا ينتقل العملاء إليه مرة واحدة بواسطة مثبّت `0.48.0` اليدوي. بعد ذلك تصل الإصدارات اللاحقة من GitHub Releases دون حذف التطبيق أو إعادة تثبيته يدوياً.

## استرجاع طارئ

لا تحذف `pos.db.key`. لاسترجاع لقطة على نفس حساب Windows، أغلق Nexora POS ثم انسخ محتويات مجلد اللقطة إلى مجلد `userData` نفسه بعد حفظ نسخة من محتواه الحالي. تحتاج القاعدة المشفرة إلى مفتاحها المطابق وعلى حساب Windows نفسه، لأن المفتاح محمي بـ `safeStorage`.
